# pjournal-pico 架构评审（2026-10-04）

评审范围：基础层（hw/gfx/font/display/crossmux）、输入法层（IME / editor_vk）、交互层
（input / ui_helpers / 共享三件套）、应用层模块化（screen_* 与 main.cpp 分发）。
方法：只读通读 + 证据定位（下文的 `文件:行号` 都可直接跳转）。**本次评审不改任何代码。**

---

## 0. 结论（先读这段）

**一句话**：核心分层的几个大决定是对的，而且比多数同类项目做得早 —— crossmux 被正确
地抽成了独立组件、虚拟键盘只有一份实现、共享交互三件套（clipboard / edit_menu /
text_sel）真的被复用了、没有任何 screen 反向依赖 main.cpp。问题不在"分层错了"，而在于
**三处接缝从来没建起来**，于是每加一个功能，落地方式都是"找到最像的那处实现、复制一份、
改两行"。

三条最贵的症状：

| # | 症状 | 代价 |
|---|---|---|
| 1 | **项目不在版本控制下**（`git rev-parse` → not a repository，父目录也没有） | 任何重构都不可回退。这是其它一切整改的前置条件 |
| 2 | **没有 Screen 接口契约** | 进入/退出/初始化/清屏策略被 11 个屏各写一遍，规则只活在 main.cpp 的注释里 |
| 3 | **`board.h` 包含 epdiy**，逼出"全局符号就地声明"的惯例 | ~35 处重复声明、两个"裸声明头"、四份 TTF 角色枚举，全是这一条的下游 |

体检表（详见 §2）：

| 层 | 结构 | 重复度 | 结论 |
|---|---|---|---|
| 基础层 hw/gfx/font/display | 中 | **差** | 依赖倒挂 + 全局符号靠手抄；推屏有 4 条并行路径 |
| 输入法层 IME / editor_vk | 好 | 中 | IME 本身的 API 干净；editor_vk 越界严重（知道设置、知道蓝牙） |
| 交互层 input / ui_helpers / 三件套 | 中 | **差** | 展平规则分两层、靠例外名单维护；横向能力大量各写一遍 |
| 应用层 screen_* | **差** | **差** | 巨型文件 + 文件级静态状态 + 无契约；但依赖方向是干净的 |

## 1. 三个症状的证据

### 1.1 不在版本控制下

```
$ git -C /home/ywz/pico/pjournal-pico rev-parse --show-toplevel
fatal: not a git repository (or any parent up to mount point /)
```

`main/screen_reader.cpp` 本身 561KB / 12219 行。**在没有 git 的仓库里谈"拆文件、抽接口"
是空话**——拆错一次就没法回退。所以整改单里的第一项永远是它，而且只花五分钟。

### 1.2 没有 Screen 接口契约

每个屏的对外形状都不一样，进入/退出的策略写死在 `main.cpp` 的 switch 里：

- 通用信号是 `xxxInited` 布尔量，每个 case 一份：`main.cpp:1319,1329,1339,1350,1360,1370,1411,1425,1439,1453,1464`。
- **GTD 是唯一的例外**：`static bool gtdInited`（`main.cpp:1381`）永不清零
  （`main.cpp:1398` 注释"故意不清"），重进只补方向。规则的理由写在 `main.cpp:722-730`
  的大段注释里，而不是写在接口上。
- 编辑器第二套：`app_editor_needs_reinit()` + `editorInited`（`main.cpp:1293-1295`），
  再加灵感/润色返回时的"会话暂存/恢复"（`screen_editor.cpp:3797-3806`）。
- 阅读器第三套：没有 `Inited`，每次 `screen_reader_init()` 自己重建大半个 `st`
  （`screen_reader.cpp:11807-11923`），靠 `s_return` 记住上次停在哪一屏。
- `reset_drawn` 只给编辑器一家（`main.cpp:1584`）。
- 虚拟键盘的"宿主名单"是 main.cpp 里手写的一串 `||`（`main.cpp:1596-1600`）。

**后果**：加一个屏要改的地方散在 3 个文件；一处漏掉就是"键盘僵在屏幕上"或"回来时
草稿没了"这类症状——都是已经发生过的 bug。

### 1.3 `board.h` 包含 epdiy → 全仓手抄全局

`main/hw/board.h:6-7` 引入 `read_pico_init.h` / `epd_highlevel.h`，而 epdiy 的
`typedef EpdFont` 与 crossmux 的 `EpdFont` class 冲突（`screen_reader.cpp:6-11`、
`board_reader.h:4-8`、`reader_page_turn.h:7-10` 三处都在解释同一件事）。于是：

- `extern u8g2_t *g_u8g2;` —— 尽管 `board.h:15` 已经声明了，**仍有约 20 个 .cpp 就地重抄**
  （`screen_editor.cpp:31`、`screen_gtd.cpp:45`、`standby_clock.cpp:24`…）。
- 15 个文件**就地重写 u8g2 原语原型**，且写成 `void*` 版绕过真头
  （`edit_menu.cpp:14-17`、`screen_gtd.cpp:49-59`…），签名已经漂移出两种写法
  （`unsigned char *` vs `uint8_t*`，见 `screen_editor.cpp:40` vs `screen_gtd.cpp:59`）；
  形参名还有直接叫 `g_u8g2` 造成遮蔽的（`screen_flomo.cpp:35`）。
- 为了绕开这个冲突，专门造了两个"裸声明头"：`hw/board_reader.h`、`reader_page_turn.h`。
- TTF 角色枚举有 **4 份拷贝**：`ttf_font.h:38-41`（权威）、`font_renderer.h:32-35`（自认复制）、
  `GfxRenderer.cpp:47-49`、`screen_reader.cpp:95-96`（`RD_TTF_ROLE_*`）。
- `screen_reader.cpp:56-99` 整段 `extern "C"` 重抄 ttf 接口。

**这一条是本次评审里性价比最高的发现**：把 `board.h` 拆成"含 epdiy 的 bring-up 头" +
"不含 epdiy 的全局符号头"，上面这一整类就消失了。

## 2. 分层体检

### 2.1 基础层

**好的部分**：`crossmux`（Epub/Txt/Xtc/GfxRenderer/HalDisplay/HalStorage/Dictionary）
抽得干净，是可复用组件；`e0470_page_turn` 独立；`fb_fast.h` 的"每 TU 一份静态几何 +
`fb_fast_sync()` 检测旋转变化"是个聪明的选择；夜间反色、bulk IO、rails keepalive 这些
硬件细节都收在 `display.c` 里。

**问题**：

1. **依赖倒挂（有环）**
   - `hw/board.cpp:9` → `ui_render.h`（板级 bring-up 依赖渲染任务层，只为 `ui_render_drain()`）
   - `ui_render.cpp:26,29` → `editor_vk.h` / `ime/IME.h`（渲染层反向依赖虚拟键盘和输入法，
     只为读 `editorVkVisible/editorVkTop`、`g_ime.composing()`）
   - `ui_helpers.cpp:4-8` → `markdown_render.h` / `wifi_manager.h` / `IME.h` / `bt_keyboard.h`
     （"基础 helper"反向依赖四个上层模块）
   - `hw/input.cpp:8` → `pjournal_app.h`（输入层依赖应用层只为拿 `KEY_*`）

2. **推屏有 4 条并行路径**（`HalDisplay.cpp:86` 自称"所有推屏的唯一出口"，实际不是）
   - A：`ui_clear/commit` → core1 渲染任务 → `render_present`（UI 通用路径）
   - B：`g_rd` 直绘 `front_fb` → `displayBuffer`（阅读器，刻意绕过 core1，有注释说明）
   - C：直呼 epdiy（`board_init` 清屏、`main.cpp:369-370` 睡眠清屏、`display.c` 内部）
   - D：`fb_fast` 直写工作缓冲（开机动画、待机表盘）

3. **反残影计数器有三套同时在记账**：`display.c:76` 的 `s_soft_refreshes`
   （`APP_GC16_EVERY=14`）、`ui_render.cpp:105-106` 的 `s_gc16_counter`/`s_follow_partials`
   （`FOLLOW_GC16_EVERY=8`）、阅读器的 `s_ghostAccum`/`s_pagesSinceFull`
   （`screen_reader.cpp:8030,8048`）。UI 路径上**同一次推屏被两层各记一次**
   （`ui_render.cpp:221` 与 `display.c:103`）。

4. **旋转映射有三份**：`fb_fast.h:41-68`、`ui_render.cpp:158-163` 的
   `diff_bounding_rect`、epdiy 内部 `_rotate`。

5. **两套"settings"**：`settings.c`（NVS 命名空间 `"pjfont"`，只存字体路径）与
   `settings_manager.cpp`（SD 文件 `/sdcard/settings/*`，22 个文件在用）。同名不同物。

6. **刷新档位靠整型位置硬绑**：`display.c:225-233` 的
   `DISPLAY_KIND_*` 与 `HalDisplay::RefreshMode` 一一对应，`display.c` 自认"顺序不能改"。

7. `FontRenderer` 的 `font_size_/line_height_/…` 是**类静态量**，被 `g_font`/`g_content_font`/
   `g_vk_font` 三个实例共享，`setSize()` 是实例方法却改全局（`font_renderer.h:106-111`）。
   头文件自己写了坑（`font_renderer.h:43-46`：任何实例调 `begin()` 都会把用户字号冲回 20pt），
   所以 `g_vk_font` 被规定不能调 `begin()`——一条只存在于注释里的约束。

**小冗余**：`ui_send_buffer()` 与 `ui_full_refresh_now()` 函数体完全相同
（`ui_helpers.cpp:529,532`）；`ui_flush_ime_deferred()` 是空函数（保留只为不改调用点）。

### 2.2 输入法层

**好的部分**：`IME` 的对外 API 是本次评审里最像样的：单例、`handleKey(int, std::string&)`
这样的纯函数式主路径、`composing()/candidates()/displayCode()` 这样的查询式状态读取、
`reset()`/`cancelComposition()` 语义清楚。歧义布局、T9、用户词库都有明确的接口边界。
**虚拟键盘只有一份实现**（`editor_vk.cpp`），阅读模式和 GTD 的旧键盘已经删干净
（`screen_reader.cpp:4859`，全仓 grep 不到 `VK_H/VK_TOP` 等旧常量）。

**问题**：

1. **`editor_vk.cpp`（1803 行）职责越界**：
   - 直接读写用户设置：`ime_cand_size`（`:52`）、`kb_layout`（`:52,393,662`）。
     布局持久化属于设置层。
   - 直接读蓝牙驱动状态：`g_bt.isConnected()`（`:666,678,686`）决定虚拟键盘是否可见。
     **这一条正是我们刚修的"虚拟键盘弹不出来"的 bug 的土壤**——键盘的可见性判断散落在
     五处（`editor_vk.cpp`、三个屏各自的 `AutoShow`、`main.cpp` 的宿主名单）。
   - 直接操作渲染栈内部：u8g2 buffer、`ttf_set_role`、`g_vk_font` 子集。
2. **候选条有两份实现**：`ui_helpers.cpp:362` 的 `drawIMEUI`（+ 三个包装）与
   `editor_vk.cpp:497/449` 的 `evkComputeCandLayout/evkCandDrawText`。各屏按"键盘可见否"
   二选一（`screen_settings.cpp:1165-1166`、`screen_gtd.cpp:2226-2227`…），两份都要维护。
3. **IME 输出落进文本框，三套实现**（这是最该合并的一处，因为它正是 VK bug 的产地）：
   - 编辑器：`editorInsertText`（`screen_editor.cpp:3827`）
   - GTD：**七个 mode 块各内联一遍** `g.editBuf.insert(...)`
     （`screen_gtd.cpp:4226,4386,4605,4966,5435,5675,5871`）
   - 阅读器：`vkTargetString/vkCommit/feedVkKey/feedVkBackspace/vkEnter`
     （`screen_reader.cpp:4909-4968`）
   退格同样三套（GTD 内部还是多份 UTF-8 退格），回车同样三套，ASCII 兜底只有编辑器和
   阅读器有、GTD 没有（**行为已经不一致**）。
4. **组合状态切界面不自动清**：`setActive()` 无论开关都 `reset()`（`IME.cpp:3078`），
   但 `reset()` 刻意不清 `_fullwidth/_trad/_english`（设计如此，是"用户偏好"）；
   于是每个界面在模式切换处**自觉**补 `cancelComposition()`（阅读/GTD/设置/灵感/润色/
   flomo 各一处）——靠调用点自觉，漏一处就是"残留组合串飘到下一个界面"。

### 2.3 交互层

**好的部分**：`input.cpp` 的事件源收得干净（触摸手势状态机 + 物理键 + 摇一摇 + 电源键
全在一个文件里），`input_tap_xy` 的"读后即清"语义简单可靠；`text_sel` 的行表模型
（宿主给 `TextSelLine*`）是最成功的共享抽象，已经接了 5 个文件 7 处字段。

**问题**：

1. **按键展平分两层，用例外名单维护**（这是最脆的地方，我们已经在
   `touch-swipe-key-flattening` 记过教训）：
   - 第一层 `main.cpp` 有 11 处改写，每处带一个例外名单（`:1015-1019`、`:1231-1234`、
     `:1250-1254`、`:1263-1271`…），名单内容是硬编码的 AppState 列表。
   - 第二层在屏幕内部：`screen_reader_handle`（`screen_reader.cpp:12001-12140`）又做一遍
     （`KEY_SHAKE`/`KEY_BACK`/`bleKeymapTranslate`/`KEY_CAP_*`/`KEY_TOUCH_LONG`/
     `KEY_LEFT/RIGHT`/`KEY_UP/DOWN`/`KEY_PAGE_*`），GTD（`screen_gtd.cpp:4100-4208`）、
     编辑器（`screen_editor.cpp:3164-3185`）各有一份。
   - **后果**：一个键的语义要在 2~3 个文件里对账。加一个界面就要在三张名单上各加一笔。
2. **坐标分流 API 有五件，语义要记住**：`input_tap_xy`（消费）、`input_tap_peek_xy`（不消费，
   只有编辑器泵在用）、`input_press_xy`（手势按下点，只本帧有效）、`input_drag_xy`、
   `input_back_dir`。peek→consume 的顺序约定写在 `text_sel.h:51-52` 的注释里。
3. **横向能力各写一遍**：
   - WiFi 连接/重试：`ui_helpers.cpp:667-687` 有通用的 `ensure_wifi_connected`，但
     `screen_settings`/`screen_flomo`/`screen_reader`/`main.cpp`/`screen_editor`/
     `screen_polish`/`screen_file_manager` 又各写一遍。
   - HTTP：6 个文件各自手搓 `esp_http_client` 生命周期（`dictionary_store.cpp:201`、
     `flomo_client.cpp:239,347`、`flomo_api.cpp:169`、`deepseek_client.cpp:71`、
     `opds_client.cpp:205`、`webdav_client.cpp:143`），进度回调也各写一套。
   - 目录枚举：7 个文件各自 `opendir/readdir`。
   - 浮层提示两套：共享 `ui_toast_*`（`ui_helpers.cpp:484-525`）与阅读器自建
     `rdShowFloat/rdShowBusy`（`screen_reader.cpp:8272`）。
   - 确认框两套：共享 `ui_draw_confirm_dialog`（`ui_helpers.cpp:639`，3 处在用）与
     GTD 自绘的 `M_CONFIRM`（`screen_gtd.cpp:4533`）。
   - 进度条：`screen_reader.cpp` 一个文件里就有 5 种画法（`:1708, 5428, 6004, 7861, 10273`）。
   - **列表滚动选择**：阅读器一个文件里 ~48 处 `Sel = max/min(...)` 单行样板，跨 15 个子界面。
   - **tap-y → 行号命中**：阅读器 ~37 处、设置 2 处、GTD 1 处，同一公式各写一遍。
4. **JSON 两套**：`json_parser.*` 与 `flomo_json.*`（后者自述是从 `../Flomo` 逐字移植的
   重复实现，`flomo_json.h:3`），`enum class JsonType` 与成员布局同构。

### 2.4 应用层 / 模块化

**好的部分**：依赖方向是干净的 —— `main.cpp` → 各 screen 单向；除了
`standby_clock → screen_reader`（借数不借绘制，有注释说明设计意图）和
`editor ↔ polish/inspiration` 的少量回调，屏之间没有互相 include 实现。
`main/CMakeLists.txt` 的 SRCS 与磁盘**完全一致**（57 个源文件，无漏列无多列）。

**问题**：

1. **巨型文件**（这就是"模块化"的实际短板）：

   | 文件 | 行数 | 里面装了什么 |
   |---|---|---|
   | `screen_reader.cpp` | 12219（561KB） | 阅读 UI + 微信读书客户端 + 图片查看器 + 词典 UI + 文件管理服务 UI + 阅读设定 |
   | `screen_gtd.cpp` | 6514 | 任务/项目/日历/便签/筛选/确认框/选择器 |
   | `ime/IME.cpp` | 6110 | 拼音+两分+歧义+T9+用户词库+学习+联想+整句 DP |
   | `screen_editor.cpp` | 3895 | |
   | `screen_outline.cpp` | 2501 | |
   | `screen_settings.cpp` | 1821 | |
   | `editor_vk.cpp` | 1803 | 见 §2.2 |

2. **超长函数**：`screen_gtd_handle` 2415 行、`screen_outline_handle` 1295、
   `app_main` 1234、`screen_editor_handle` 754、`screen_settings_handle` 550。
   阅读器有 44 个 `handleXxx(int key)`（最长的 `handleNetShare` 1014 行），
   由一个 43 分支的 `switch (st.mode)` 分发（`screen_reader.cpp:12154-12197`）。

3. **状态全在文件级静态里**（11 个屏 11 份：`st`/`g`/`g_settingsState`/`g_editor`…），
   配套的是"谁在什么时候清"这套隐性约定——见 §1.2。这是 §1.2 的病根。

4. `screen_inspiration` 没有自己的 `.h`，入口声明借住在 `pjournal_app.h:145-146`。

## 3. 整改方案

原则：**小步、每步可独立验证、每步都能用构建/上机验回**。顺序按"性价比 × 风险"排，
前两批几乎是零行为变更的机械操作，第三批开始才是真正的设计改动。

### P0 · 安全带（今天，5 分钟）

1. `git init` + `.gitignore`（`build/`、`managed_components/` 视情况、`sdkconfig` 保留）
   + 一次 baseline 提交。
2. 把 `/tmp` 里那几个主机端探针（`ambig_probe`、`epubprobe`、`fnprobe`、`fontprobe`）
   收进 `tests/host/` 并写一个 README 说明怎么跑。

**理由**：后面每一批都要求"拆错了能回退"和"主机端能验"。
**验证**：`git status` 干净；探针在新路径下能跑。

### P1 · 纯机械清理（零行为变更，一次做完）

1. **拆 `board.h`**：新建 `hw/board_globals.h`（只含 `u8g2_t` 前向声明 + `extern g_u8g2` +
   `g_hw` 的**不透明**声明，不引 epdiy），`board.h` 包含它。
2. 删掉 20 处就地 `extern u8g2_t *g_u8g2;` 和 15 处手抄 u8g2 原型，统一 include
   `gfx/u8g2_shim.h` + `hw/board_globals.h`。**顺便修签名漂移**（`void*` → `u8g2_t*`）。
3. 删 4 份重复的 TTF 角色枚举，统一到一份"不含 epdiy 的"薄头（把 `ttf_font.h:38-41`
   单独提到 `font/ttf_role.h`，其余三处 include 它）。
4. 删 `ui_flush_ime_deferred()`（空函数）与它的 4 个调用点；把
   `ui_send_buffer()`/`ui_full_refresh_now()` 合并成一个（保留两个名字做 inline 别名也行，
   但注释要写清为什么）。
5. 重命名 `settings.c` 的 API 为 `font_store_*`（文件重命名为 `font_store.c/.h`），
   消除与 `settings_manager` 的同名混淆。
6. `screen_inspiration` 补一个 `.h`，把 `pjournal_app.h:145-146` 的两个声明搬过去。

**理由**：这些都是"照着现在的代码抄一遍"的工作，不改变任何行为，但会让之后每一步
都少踩一次坑。第 1~2 条尤其关键：它一次性消灭"裸声明头"这个类别。
**验证**：`idf.py build` 通过；binary size 变化应在几百字节内。
**风险**：低。唯一要小心的是 `void*` → `u8g2_t*` 的类型收紧可能暴露隐藏的错误调用
（那正是好事）。

### P2 · 三个共享服务（真正的设计改动，各可独立做）

**2a. `ui/ime_field.h` —— 文本字段绑定**（最优先）

```cpp
struct ImeField {
  std::string *text;      // 目标串
  int maxBytes;           // 0 = 不限
  bool multiline;
  size_t cursor;          // 光标（字节偏移），由字段自己维护
};
bool imeFieldFeedKey(ImeField&, int key);      // → IME::handleKey + 落串
void imeFieldBackspace(ImeField&);             // UTF-8 安全的退格
bool imeFieldEnter(ImeField&);                 // 提交语义（换行 or 提交）
void imeFieldInsertText(ImeField&, const char*); // ASCII 兜底 / 剪贴板
```

替换：编辑器 `editorInsertText`、GTD 七处内联 insert + 七处退格、阅读器
`vkTargetString/commitVk/feedVkKey/feedVkBackspace/vkEnter`。
**理由**：这是 VK 相关 bug 的产地（我们刚修的"弹不出来"和历次退格/回车问题都在这一层）。
一份实现 = 一处修、处处修。GTD 缺 ASCII 兜底这类"三份实现漂移"也一并消灭。
**验证**：三个模式各做一轮 输入/退格/回车/中英切换；`text_sel` 与剪贴板路径不受影响。
**风险**：中。三个宿主的光标/滚动语义有细微差别（阅读器的输入框有"确认键先弹键盘"的逻辑），
要先在 `ImeField` 里留出"宿主钩子"，不能硬套。

**2b. `net/http.h` —— 一个 HTTP 客户端**

统一 6 处手搓 `esp_http_client`：`GET/POST + headers + body + 进度回调 + 可中止`。
把我们已经踩过的两个坑直接烧进接口注释：`set_timeout_ms(client,1)` 才中止得了
（见 `http-client-abort-trickling`）、`HalFile::read` 返回 int 别塞 `size_t`。
**验证**：词典下载、flomo 发送、OPDS、WebDAV、DeepSeek（润色）各跑一次。
**风险**：中低（各站点的 header/认证差异要在参数里留出口）。

**2c. `ui/list_view.h` —— 列表选择/滚动/命中**

```cpp
struct ListView { int first, sel, count, itemH; int top; int visible; };
void listViewKey(ListView&, int key);          // 上/下/翻页/首页尾页
void listViewScrollTo(ListView&, int idx);
int  listViewHitAt(const ListView&, int y);    // tap-y → 行号，越界返回 -1
```
替换阅读器 ~48 处样板 + 15 个各自算 top 的 helper（`fbListTop`/`weMenuFirstY`/
`wifiListTop`/`opdsListTop`/`resListTop`/`netListTop`…其中 4 个公式完全相同）+ 40 处
tap-y→行号。
**验证**：阅读器各列表页上下翻、点选、边界（空列表、只剩一行）。
**风险**：低-中（纯算术，但影响面广，建议先只换阅读器里最像的那几个子界面，
不搞一次性全量）。

### P3 · Screen 接口 + 拆巨型文件

**3a. Screen 接口**

```cpp
struct Screen {
  const char *name;
  void (*init)(ScreenContext&) = nullptr;
  AppState (*handle)(int key, ScreenContext&) = nullptr;
  void (*idle)(ScreenContext&) = nullptr;
  void (*exit)() = nullptr;
  bool keep_alive = false;   // true = 切模式时不重跑 init（GTD 的现有语义）
};
extern const Screen kScreens[APP_QUIT + 1];
```

把 `main.cpp` 里每个 case 的 `xxxInited` 策略、`reset_drawn`、`editorVk` 宿主名单、
`setPageSize` 之类的每屏准备动作，全部变成表里的字段或 `init/exit` 内部的事。
**理由**：§1.2 的所有症状一次性解决；加一个新屏 = 表里加一行。
**验证**：逐屏进出 × 模式轮换（阅读↔写作↔计划）的回归清单。
**风险**：中。要严格保持现有语义（尤其 GTD 的"本次开机只 init 一次"），
建议先只建表、保持每个 case 的代码原样搬进去，再逐个屏精简。

**3b. 拆 `screen_reader.cpp`（12219 行）**

按子应用切，边界是现成的（44 个 handler + `switch (st.mode)` 的 43 个分支）：
`shelf`（书架/最近/搜索）、`toc`、`read_settings`、`net_share`（微信读书，1014 行）、
`browser/http`（689 行）、`image viewer`、`dict_ui`、`file_manager_ui`。
`st`（`RdState`）保留在 `screen_reader_internal.h` 里共享。
**风险**：中高，但收益最大（单文件 561KB 已经影响编译和阅读）。
**建议**：先拆出最独立的 `net_share`（1014 行、依赖最少）验证手法，再拆其余。

**3c. 拆 `screen_gtd_handle`（2415 行）**：按 `M_*` mode 拆成
`handleAdd/handleEditField/handleEditNote/handleBrowse/handleFilter/...`，
用 3a 建的表驱动。同理 `screen_outline_handle`（1295）。

### P4 · 推屏路径统一（最后做，风险最高）

把 4 条路径收敛到一个 `present(rect, RefreshMode)`，`display.c` 只保留"波形选择"这一件事；
三套反残影计数器合并成一个（放在 `display.c`，因为只有它知道真实波形）；
旋转映射只保留 `fb_fast` 一份，`ui_render` 的 `diff_bounding_rect` 复用它。
**为什么放最后**：这是我们最不能出错的路径（残影/闪烁/死机都在这儿），
而且 P1-P3 做完之后它会好改得多。**动之前必须在主机端有等价性对拍**（现有的
`epd-layout-host-harness` 和 `epd-fast-draw-path` 里的随机对拍就是干这个的）。
